Semantic Communications Benchmark Harness — v7

Semantic communication gains, benchmarked head-to-head

A matched benchmark harness for task-oriented communication. Same task, same channel, same transmit power — Semantic coder against two conventional baselines — swept over SNR, with Monte Carlo variability, full provenance, and downloadable results. The headline baseline is the smart system: the smarter conventional system already used in real IoT and edge devices — still separate source + channel coding, bit-exact, with ARQ — which sends only a locally produced label / intent / command / event code where the task allows it, and most of the content where the task needs more than a label. The full-source conventional system — the whole source, bit-exact, every time — is kept alongside as a clearly labelled secondary reference. Semantic gains are headlined against the smart system, and the full-source comparison is shown alongside it, so both comparisons are visible and neither is hidden. Change any assumption and the gains move with it. The results below are presented as a showcase view: only the cases where the Semantic coder improves on the smart system headline baseline are displayed.

Assumption — task success is assumed · Tasks are implemented gainfully

Task success is assumed throughout this harness. Tasks are assumed to be implemented gainfully — the task succeeds — and efficiency metrics are gains under that assumption, each on a clearly labelled basis: success-based measures (successful tasks per joule, joules per successful task, transmit-power saving at matched success) are measured per successful task; cost measures labelled “per task” (energy, symbols, bandwidth, latency and compute per task) are measured per attempted task — the cost of sending one task — and are labelled that way wherever they appear. Under the assumption an attempted task is a task that succeeds, so those per-attempt costs are the costs of a successful task; outside it, they are attempt costs. They are not gains for a failed task: if a task does not succeed, its efficiency does not count as a gain. Read every efficiency result on this page, in every chart, table, verdict and download, on that basis.

Reference preset — published behaviour · not measured by this harness

DeepJSCC for Picture — Bourtsoulatze, Kurka & Gündüz (2019)

This panel describes published reference behaviour from the original Deep Joint Source-Channel Coding (DeepJSCC) paper, so the harness’s Picture setup can be read against the closest published reference system. It is a literature reference, not a harness run: no number in this panel was produced by this harness, and none of the paper’s numbers are reproduced here — the behaviour is summarised qualitatively, in words and in the schematic below.

SourceE. Bourtsoulatze, D. Burth Kurka and D. Gündüz, “Deep Joint Source-Channel Coding for Wireless Image Transmission”, IEEE Transactions on Cognitive Communications and Networking, 2019. An open-source PyTorch implementation accompanies the paper; it is not embedded or run in this page.
ArchitectureA convolutional neural network (CNN) autoencoder. The encoder maps the image pixels directly to channel symbols — a fixed number of complex-valued symbols per image (set by the bandwidth ratio) — with no bits and no separate source or channel coding stage. The channel adds noise or fading, and the CNN decoder reconstructs the image from the received symbols. The pair is trained end-to-end through the channel model.
Task & data in the paperImage reconstruction, evaluated on CIFAR-10 (32×32 colour images), with quality reported as PSNR. Note the difference: this harness’s Picture task is a task-success model, not PSNR reconstruction — the two results are not the same metric and are not merged anywhere on this page.
Channels in the paperAWGN, and slow (block) Rayleigh fading — which is why this preset applies only with the harness channel set to AWGN, or to Fading with Fading type = Rayleigh.
Baselines in the paperJPEG and JPEG2000 source coding followed by a capacity-achieving channel code — an idealised separation-based baseline (the best a separate source + channel scheme could do in theory), not a practical modem.
Published behaviour (qualitative)Graceful degradation, no cliff: as SNR falls, DeepJSCC’s reconstruction quality falls smoothly. The separation baseline instead shows a cliff effect — once SNR drops below what its channel code needs, decoding fails and quality collapses. The paper reports DeepJSCC performing better than even that idealised baseline particularly at low SNR and low bandwidth ratios, and remaining competitive as SNR rises; a network trained at one SNR also degrades gracefully when the actual channel SNR differs, rather than failing abruptly.

Kept separate: everything below this panel — charts, Efficiency panel, verdicts, tables and downloads — is this harness’s own simulated / modelled output under the menus on the left. Selecting this preset aligns the harness setup with the paper’s conditions and records the preset in the reproducibility log; it does not replace, rescale or validate the harness’s numbers.

Error rates — at a glance

Task error = 1 − task success. BER = uncoded bit error rate, modelled from the effective SNR and modulation (Q-function) — the same physical channel for all three systems. BLER = conventional block error rate, per single attempt and after ARQ retries — both conventional baselines (smart system and full-source) share the same channel code, modulation and ARQ model, so their per-attempt BLER is the same; they differ in how much they send, not in how each attempt is coded. SER = symbol error rate derived from BER. Feature error = share of Semantic coder features corrupted beyond tolerance — the Semantic coder has no blocks, so it has no BLER; its errors show up as feature and task errors instead. All error rates are simulated / modelled, not measured.

3 — Efficiency panel — efficiency gains, each on its labelled basis (task success assumed)

Assumption — two labelled bases, do not mix them: task success is assumed and tasks are implemented gainfully. Success-based measures in this panel — successful tasks per joule, joules per successful task, and transmit-power saving at matched success — are gains per successful task. Cost measures labelled “per task” — joules per task, symbols per task, transmitted bits per task, latency per task and compute per task — are per attempted task: the cost of sending one task, whether or not it succeeds. “Per task” in this panel never means per successful task. Under the assumption an attempted task succeeds, so those per-attempt costs are the costs of a successful task — but an efficiency figure is not a gain for a failed task.

“Efficiency” here is five different things, shown separately so no single number has to carry the whole story. Every gain in this panel is shown twice: the headline gain against the smart system baseline, and the gain against the full-source conventional baseline as a secondary reference — neither comparison is hidden. The headline energy measure is successful tasks per joule / joules per successful task (per successful task). Energy efficiency — how much transmit energy a task costs, as joules per attempted task and as joules per successful task. Spectrum efficiency — how much channel occupancy one attempted task costs. Bandwidth efficiency — how much transmitted data volume one attempted task costs. Latency efficiency — how many tasks per second the link delivers, from the latency of one attempted task. Compute efficiency — the encoder cost per attempted task that the Semantic coder pays to buy the other gains; it is shown as a cost, not hidden. Where task success only ties with the baseline — typically at high SNR — the panel marks exactly which efficiencies the Semantic coder still wins on.
